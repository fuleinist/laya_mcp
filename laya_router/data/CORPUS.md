# The labelled corpus: where it came from and how it was labelled

`steps.jsonl` is the data step 1 of issue #3 is measured on: one JSON object per line, each with a
`task` (what a step is about to do), gold `labels` for the three questions in
`laya_router/data/questions.json`, and a `provenance` field naming the artifact it came from.

```
{"id": "...", "task": "...", "labels": {"tier": "economy|frontier", "needs_tools": true|false,
 "sensitive": true|false}, "kind": "task|question", "provenance": "..."}
```

## Provenance rule

Every item is a real artifact from this machine, paraphrased into the shape a router actually
receives (a one-line description of the work). Nothing here was invented for the eval, and
nothing was generated by a model:

| source | count | what it is |
|---|---:|---|
| commits | 47 | commit subjects and bodies from `effected` (10), `wigolo` (10), `skillforge` (8), `pr-sage` (5), `laya_mcp` (4), `tabularis-dynamodb-plugin` (3), `harness-lab` (3), `model-router` (2), `repoguard` (1), `agent-sandbox-mcp` (1) |
| docs | 9 | the typed questions a computer-use loop asks, taken from the patterns in `docs/computer-use.md` §4 and `docs/computer-use-api.md` §4 |
| issues | 6 | open issues in `fuleinist/laya_mcp` (including #3 itself and its build-order items) and `fuleinist/skillforge` |
| pull requests | 4 | open and merged PRs in `fuleinist/laya_mcp` |
| cron jobs | 4 | the scheduled jobs configured in this Hermes profile |
| step logs | 3 | review and planning questions this repo's own step logs produced |

73 items in total: 61 `task` items and 12 `question` items. Tier split 38 `economy` /
35 `frontier`; `needs_tools` 62 true / 11 false; `sensitive` 8 true / 65 false (releases, merges and
credential fixes carry the flag).

Two kinds of item, because a loop routes two kinds of step: `task` items are work to be performed,
`question` items are decisions over text already in hand (the `needs_tools` flag is what separates
them here — the corpus needs both, or that flag has no variance to measure).

Sanitisation: absolute paths were replaced with `<path>`-shaped wording, e-mail addresses and
personal names were dropped, and each item was condensed to one or two sentences. Private
repository content is not reproduced; provenance points at it instead.

## Labelling rubric

Written down before labelling, and applied in that order. `tier` answers "how much reasoning does
this step need", not "how many files does it touch" — a mechanical edit across five files is still
`economy`.

**`tier`**

| label | rule |
|---|---|
| `economy` | Bounded, and the target is already known: a mechanical edit, a version or dependency bump, a documentation or comment change, a test for behaviour that already exists, a release, a lookup, or a command to run. A small model one-shots it without exploring. |
| `frontier` | Needs exploration before it can be done: designing something whose shape is not decided yet, debugging across components, a change whose blast radius makes an early wrong move expensive, or an open-ended loop of many tool calls. |

**`needs_tools`** — to finish the step, does the agent have to act outside its own context (edit
files, run commands, call an API, look something up), rather than reasoning over text already
provided?

**`sensitive`** — is the step irreversible, destructive or credential-bearing: publishing a release
or artifact, force-pushing or rewriting history, deploying, rotating or touching secrets, moving
money, deleting data, or running untrusted code on a primary machine?

### Judgement calls, recorded

* **Releases and merges are `economy`, not `frontier`** — the procedure is known and bounded — but
  they are `sensitive: true`, because publishing cannot be taken back. Keeping the two axes apart is
  the point: the flag is not a difficulty proxy.
* **Doc PRs in this repo are `frontier`.** `docs/computer-use.md` required interpreting its own
  measurements; "write the docs" is not bounded when what the docs should say is the open question.
* **A refactor is `economy`.** Extracting duplicated components is mechanical even though it spans
  files; nothing has to be discovered.
* **`question` items are `economy` by construction**, with the two exceptions that turn on open
  evidence (`q-latency-budget`, `q-third-tier`). They exist to give `needs_tools` variance and to
  cover the verification steps a computer-use loop actually asks.

## Limitations — read these before quoting a number

1. **One labeller.** These are my labels, applied with the rubric above. The study's own warning
   applies: blind agreement between independent labellers topped out at 0.82, so a few points of
   difference is noise, not a result. The frontier backend's own accuracy against these labels *is*
   the agreement measurement, and it is reported in the same table.
2. **Size.** 70+ items supports a paired comparison and a rough interval, not a confident ranking.
   The accuracy CIs are in the results; if they overlap, the honest reading is "not separated".
3. **Bias towards this machine's work.** The corpus is a set of tasks this machine did. A different
   mix of work would move both backends.
4. **The prompt is short on purpose.** A router in a loop sees the step description and whatever
   history the caller passes; it does not see the repository. Both backends receive the same state.

## Extending it

Append lines with a unique `id`, the three labels and a `provenance` string — `load_corpus()`
validates the shape and rejects unknown tier labels or duplicate ids. Then re-run the eval with the
same command recorded in the results JSON; the corpus digest in that file tells you whether the
numbers are comparable.
