bottom line The server is healthy and its measured behaviour is documented and reproducible — but the logs contain no record of an agent ever calling it. Treat this as a build-and-measure record, not a usage record. Findings 1–5 are what I would fix before wiring it further.

Where the tokens go

The encoder's cost is questions × (state + question text), not state + questions — the state is re-read per question. 7 questions on a 1,606-char diff ≈ 4,600 input tokens; 7 questions on a 92-char diff still ≈ 1,072; 95.1% of calls exceed the documented 768-token state budget. Hence the shipped advice: ask few, terse questions per call. That is also why verify_step's own MCP latency is not the whole story — its cost is in the question text, not the diff.

07

Findings to review

Ordered by what I would fix first. Nothing here is a claim about accuracy — that is sections 05–06.

  1. No usage telemetry exists, so "usage" cannot be measured from logs.high The only counter is laya_health's calls field, which is an in-process integer (laya_mcp_server.py: self._calls = 0) that dies with the process — the 17 restarts in this window each reset it to zero, and MCP tool calls are never persisted anywhere. A one-line JSONL append in the tool wrapper (name, ms, question count, outcome) would make the next report answer the actual question: who calls this, how often, how fast, and does it ever fail.
  2. Zero recorded agent invocations in 58,864 stored messages.high Every quality number in this report comes from eval harnesses; the tools have been discovered and registered 5 times but never driven by a model in a real turn (as far as Hermes' store shows — OpenClaw keeps no tool-call log, so it is unmeasurable there). Consistent with that: since the engine child is spawned lazily on the first daemon-touching call, an unused server leaves no engine process and no indirect trace either (measured — section 02). Before adding a ninth tool, I would spend one session actually using the eight that exist, because the router/verify verdicts were derived from offline corpora, not from decisions the agent needed.
  3. smoke.log in the repo root is stale and contradicts the suite.medium It says "six tools", 21/21 passed, 19 tool calls; after warm-up p50=31 ms, max=62 ms, total=2069 ms and is dated 2026-09-24 12:15:07. tests/smoke_mcp.py now asserts 8 tools and today's run is 32/32 passed / 32 assertions. Either re-capture it or delete it — a stale green log at the repo root is the artifact a reader trusts first.
  4. Documented test counts drifted (21/21 passed → 27/27 → 32/32).medium docs/router-service.md states "27/27 passed" and "Tools discovered: 7"; the suite asserts 8 tools and 32 assertions as of this run, and 96cb0f9 already had to correct a tool count in the design notes. Referencing the command instead of the count would stop this recurring.
  5. Both harness configs carry env for tools that no longer exist.medium ~/.hermes/config.yaml and ~/.openclaw/openclaw.json both set LAYA_BROWSER_DIR=G:/dev/AI/laya/laya-browser/v10s and LAYA_BROWSER_PYTHON, pointing at a browser-agent worker that is not in the repo and registers no tool. Dead config that reads like a feature.
  6. Two of the three shipped tools are already declining to be trusted, in their own descriptions.medium route_step and verify_step both embed advisory: true, a boundary string and their measured accuracy in every payload — good practice, but it means an agent reading a confident sensitive: true (precision 0.208) has no signal in-band that it is close to a coin flip. If these stay advisory, the confidence values probably need a calibrating refit before anything reads them as numbers rather than hints.
  7. Calibration is untuned, and one field is actively misleading.low Tier ECE 0.148 with the stock checkpoint, and per docs/router-service.md §4 the daemon reported confidence = 0.0033 on a two-option choice while its options sat at 0.466/0.534 (that one is a doc figure — I did not re-measure it). The eval scores ECE from probabilities for exactly this reason, so anything consuming confidence directly is reading the wrong field.
  8. Headroom's crash loop is a bigger log problem than anything Laya does.low mcp-stderr.log is 204 MB, and 95,709 of its start banners are headroom (ImportError: MCP SDK not installed on repeat). It makes every grep in this report slower and forces rotation; unrelated to Laya, but it is why the MCP log is unreadable at a glance.
